Resultado F1.C1 · MovieCatalogLookupResult

Contrato do lookup: input com query/ano e união discriminada por found, sem HTTP nem IA.

Como funciona

Sucesso carrega MovieCatalogDetails inteiro. Miss (vazio ou TMDB fora) só traz message.

export type MovieCatalogLookupFound = {
  found: true;
  details: MovieCatalogDetails;
};

export type MovieCatalogLookupMiss = {
  found: false;
  message: string;
};

export type MovieCatalogLookupResult =
  | MovieCatalogLookupFound
  | MovieCatalogLookupMiss;

Dados fluindo

{ query: "Interestelar", year: 2014 } → found: true + details (id TMDB, imdbId, …) query vazia / TMDB 502 → found: false + message

Conecta

  • Reusa MovieCatalogDetails.
  • Consumido pelo chunk da tool de lookup.

Serviço F1.C2 · MovieCatalogLookupService

Orquestra search + details no catálogo e nunca relança falha HTTP: miss estruturado para o agente seguir.

Como funciona

Query vazia sai cedo. Ano opcional entra no texto da search. Primeiro hit vira details. TmdbHttpException e erro inesperado viram found: false com log.

const searchQuery = MovieCatalogLookupService.buildSearchQuery(input);
const searchPage = await this.catalog.searchMovies(searchQuery);
const firstHit = searchPage.results[0];
if (!hasSearchResults) {
  return this.miss(`Nenhum filme encontrado para "${searchQuery}".`);
}
const details = await this.catalog.getMovieDetails(firstHit.id);

Dados fluindo

{ query: "Interestelar", year: 2014 } → search "Interestelar 2014" → primeiro id → getMovieDetails → found: true + details TMDB 502 → found: false + message (sem throw)

Conecta

  • Usa IMovieCatalogProvider.
  • Devolve o contrato do chunk de Resultado.
  • Quem instancia o serviço é a factory de recommendation (C5), com new.

Schema F2.C1 · MovieRecommendationSchema

Separa o card público (sem ids) do schema interno do LLM, que aceita tmdbId e imdbId opcionais.

Como funciona

O DTO HTTP continua no schema público. O structured output passa a validar o schema interno via .extend.

export const SingleMovieReccomendationInternalSchema =
  SingleMovieReccomendationSchema.extend({
    tmdbId: z.number().optional(),
    imdbId: z.string().optional(),
  });

export const MovieRecommendationSchema = z.object({
  movies: z.array(SingleMovieReccomendationInternalSchema).min(0).max(3),
  response: z.string().nonempty(),
});

Dados fluindo

filme sem ids → parse interno OK filme com tmdbId 157336 e imdbId tt0816692 → parse interno OK DTO HTTP → ainda só o schema público

Conecta

  • Provider de recommendation usa MovieRecommendationSchema.
  • DTO importa só SingleMovieReccomendationSchema.
  • O strip HTTP vem no chunk do Controller.

Adapter F2.C2 · lookupMovies

Expõe a tool Zod do agente: uma chamada com 1–8 queries e Promise.all no lookup unitário.

Como funciona

AITools.createTool com schema do Zod do app (as never por mismatch de versão). schema.parse tipa o input; cada item vira lookup; o array sai na mesma ordem.

const lookupPromises = input.queries.map((queryItem) => {
          return catalogLookup.findDetailsByTitle(lookupInput);
});
const lookupResults = await Promise.all(lookupPromises);

Dados fluindo

{ queries: [{ query: "Interestelar", year: 2014 }, { query: "Duna" }] } → Promise.all de 2 lookup → [found true + details, found true|false] Zod rejeita 0 ou 9 queries

Conecta

  • Usa MovieCatalogLookupService do domínio.
  • O provider passa o retorno de createLookupMoviesTool() em agent.tools.

Prompt F2.C3 · MovieRecommendationPrompts

O system prompt unificado ensina o lote de candidatos, uma chamada a lookupMovies e a cópia de ids só quando found: true.

Como funciona

Três parágrafos novos no meio do texto: gerar 4–8 candidatos, chamar a tool uma vez com 1–8 queries, depois escolher 0–3 e copiar tmdbId/imdbId sem inventar. O restante (card, response, sem markdown) permanece.

Antes de montar o JSON final, pense em mais títulos candidatos...
chame a tool lookupMovies uma única vez... { queries: [{ query, year? }] }...
se ... found: true, copie tmdbId e imdbId ... Se found: false, ... sem incluir tmdbId nem imdbId.

Dados fluindo

pedido do usuário → 4–8 títulos candidatos → uma lookupMovies com queries → 0–3 filmes no JSON, ids só se found true

Conecta

  • Lido pelo provider de recommendation no chunk seguinte.
  • O nome lookupMovies bate com MovieCatalogLookupAiTool.TOOL_NAME.

Provider F2.C4 · AiMovieRecommendationProvider

A invoke structured passa a tool injetada em agent.tools e continua parseando o schema interno.

Como funciona

O construtor recebe Params com ai e lookupMoviesTool. Não instancia HTTP/TMDB. A factory ainda precisa injetar a tool real (próximo chunk).

const lookupMoviesTool = this.params.lookupMoviesTool;
const result = await this.params.ai.callStructuredOutput({
  aiModel: AiModels.PRIMARY,
  systemPrompt,
  messages,
  threadId: chatId,
  outputSchema: MovieRecommendationSchema as never,
  agent: { tools: [lookupMoviesTool] },
});

Dados fluindo

Params { ai, lookupMoviesTool } → callStructuredOutput com agent.tools[0] → result.response → MovieRecommendationSchema.safeParse (ids opcionais OK)

Conecta

  • Lê MovieRecommendationPrompts.unified().
  • A tool vem de MovieCatalogLookupAiTool.createLookupMoviesTool() na factory.

Factory F2.C5 · MakeGetMovieRecommendationUseCaseFactory

O bootstrap do POST monta catálogo → lookup → adapter Zod e injeta Params no provider. Sem factory extra para o serviço.

Como funciona

buildAiConfig e new AI ficam iguais. Em seguida intermediários nomeados: TMDB factory, new MovieCatalogLookupService, MovieCatalogLookupAiTool, tool, provider.

const catalog = MakeTmdbHttpClientFactory.create();
const catalogLookup = new MovieCatalogLookupService(catalog);
const lookupMoviesAiTool = new MovieCatalogLookupAiTool(catalogLookup);
const lookupMoviesTool = lookupMoviesAiTool.createLookupMoviesTool();
const movieRecommendationProvider = new AiMovieRecommendationProvider({
  ai,
  lookupMoviesTool,
});

Dados fluindo

request POST /movie/recommendation → factory.create() → AI + lookupMoviesTool → use case com provider

Conecta

  • GET /movie/queries usa outra factory — sem esta tool.
  • O controller stripa ids no schema público antes do send.

HTTP F2.C6 · MovieRecommendationController

O POST público mapeia cada filme pelo schema do card, sem tmdbId/imdbId. Destructuring do use case não basta.

Como funciona

toPublicResponseBody faz SingleMovieReccomendationSchema.parse por item (Zod strip). Os dois send (logado e guest) usam o mesmo body.

const publicMovies = movies.map((movie) => {
  const publicMovie = SingleMovieReccomendationSchema.parse(movie);
  return publicMovie;
});
const responseBody: MovieRecommendationResponseDTO = {
  response,
  movies: publicMovies,
};

Dados fluindo

filme interno { title, …, tmdbId, imdbId } → parse schema público → JSON sem ids movies [] → { movies: [], response }

Conecta

  • DTO HTTP já lista o schema público; o parse no controller é o que impede o vazamento.
  • Cota anônima e cookie seguem iguais.
